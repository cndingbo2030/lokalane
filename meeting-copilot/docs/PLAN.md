# Meeting Copilot：架构与开发计划

> 目标：一个能接入 **Google Meet / Microsoft Teams / Zoom / 腾讯会议（VooV）** 链接的会议工具，支持**在线录音、实时字幕、实时翻译**，并在对方提问或提出异议时由 AI **实时给出可以直接说出口的回应**，会后自动生成纪要与跟进邮件。

本文件是总体设计与路线图。第 0 阶段（MVP）的代码已经在本目录实现，运行方式见 [README](../README.md)。

---

## 1. 核心判断（决定成败的 6 个设计决策）

| # | 决策 | 原因 |
|---|------|------|
| 1 | **"我"和"对方"分两路音频采集、两路识别**（麦克风 = 我，会议音频 = 对方） | 不依赖说话人分离（diarization）就能 100% 知道是谁在说话。AI 只对**对方**的问题给建议，不会去"回答"用户自己的提问；纪要里的"谁承诺了什么"也更准确。这是本产品最重要的一条架构决策。 |
| 2 | **先做"标签页/系统音频采集"，再做"机器人入会"** | 机器人入会每个平台都要单独适配，而且受平台政策限制（腾讯会议没有公开的第三方入会 API）。浏览器标签页采集**今天就能覆盖四个平台**（它们都有网页版），不需要任何平台审批。 |
| 3 | **语音识别（STT）可插拔，默认 Soniox** | 中英混说是目标用户的常态。Deepgram Nova-3 的 `multi` 多语言模式支持的语种**不含中文**（中文只能单语种识别），而 Soniox 实时模型支持多语种混说识别并附带语种标签。接口已抽象，Deepgram / 自建 FunASR 可随时替换。 |
| 4 | **两级触发：规则先筛，模型再判断** | 每句话都调大模型既慢又贵。第一级是微秒级的正则/规则（问句、异议关键词、冷却时间），第二级由模型决定是否值得给建议（不值得就输出 `SKIP`，界面完全不显示）。 |
| 5 | **流式到底** | STT 部分结果实时上屏；AI 建议逐字流式显示；用户在对方说完后 1–2 秒内就能看到第一行建议。 |
| 6 | **默认隐私优先** | 录音只保存在用户本地浏览器；服务器不落盘音频；API 密钥只在服务端；开始前必须勾选"已告知并取得与会者同意"。 |

## 2. 如何"接入"四个会议平台

| 方式 | 原理 | 覆盖 | 优点 | 缺点 | 阶段 |
|------|------|------|------|------|------|
| **A. 浏览器标签页采集**（已实现） | 用户在新标签页用网页版入会，本工具通过 `getDisplayMedia` 共享该标签页音频 + `getUserMedia` 采集麦克风 | Meet ✅ Teams ✅ Zoom ✅（自动改写为 `/wc/join/` 网页入会链接） 腾讯会议/VooV ✅（网页入会） | 零审批、零安装、四平台通用、对方看不到机器人 | 需要用户每次选择标签页；依赖 Chrome/Edge | **0** |
| **B. 桌面端系统音频回环**（已实现） | Electron 桌面应用采集系统输出音频（Windows loopback；macOS 视系统版本）+ 麦克风 | 任意会议软件（含桌面客户端） | 不用网页版；置顶悬浮提词器；对屏幕共享隐藏 | 需要安装和系统权限 | 2 |
| **C. 会议机器人入会** | 服务器端无头浏览器或平台 SDK 以"XX 的会议助手"身份加入会议 | Meet、Teams（网页访客入会）；Zoom（Meeting SDK，需按 Zoom 当前政策取得加入外部账号会议的授权，上线前必须复核）；腾讯会议 ❌ 无公开入会 API → 用 A/B | 用户不用开电脑也能录；可结合日历自动入会 | 每平台单独维护；平台改版易失效；需审批 | 3 |

> "买而不建"：Phase 3 的机器人方案选用开源的 [Attendee](https://attendee.dev)（可用托管服务，也可自部署，数据留在自己的基础设施），各平台入会适配由其维护；我们只接收实时混音。Recall.ai 一类商业服务可作为备选，接入方式相同（机器人 → wss 实时音频）。

本仓库的链接解析器（`src/shared/meetingLink.ts`）已能从整段邀请文字中识别平台、会议号和密码。

## 3. 系统架构

```
 浏览器（Chrome / Edge）                                    服务器（Node.js）
┌──────────────────────────────────┐   WebSocket   ┌────────────────────────────────────────────┐
│ 会议标签页音频 ─┐                 │  二进制帧:     │ MeetingSession（每个会议一个）               │
│                ├─ AudioWorklet   │  [1B 来源][PCM]│   ├─ STT 流（me）   ─┐                      │
│ 麦克风 ────────┘   → 16kHz 重采样 │ ─────────────▶ │   ├─ STT 流（remote，开启说话人分离）       │
│                    → 100ms 分帧  │                │   │                  ▼                      │
│ MediaRecorder → 本地 WebM 录音    │                │   │        统一的"句子"结果（部分/最终）     │
│                                  │  JSON 消息:    │   ├─▶ Translator（Claude，最终句、非目标语言）│
│ 实时字幕 / 翻译 / AI 建议 / 纪要  │ ◀───────────── │   ├─▶ TriggerDetector ─▶ Copilot（Claude）   │
└──────────────────────────────────┘                │   └─▶ TranscriptStore ─▶ Summary（Claude）   │
                                                    └────────────────────────────────────────────┘
                                                         │ Soniox / Deepgram 实时 STT（WebSocket）
                                                         │ Anthropic Messages API（流式）
```

关键点：

- **线路协议**（`src/shared/protocol.ts`）：二进制帧第 1 个字节是音频来源（0 = 我，1 = 对方），后面是 16 kHz 单声道 16-bit PCM；文本帧是 JSON 消息。
- **STT 适配层**（`src/server/stt/`）：把各家原生事件统一成"句子"语义——部分结果不断替换，最终结果关闭这一句。Soniox 以 `<end>` 端点标记或说话人变化断句；Deepgram 合并多个 `is_final` 片段直到 `speech_final` / `UtteranceEnd`。
- **会话编排**（`src/server/session.ts`）：每路音频懒加载一个 STT 流（没开麦就不产生费用）；句子 ID 带会话前缀，断线重连后不会冲突。
- **背压**：上行拥塞时浏览器丢弃音频帧而不是排队——迟到的音频比缺一小段更糟。

## 4. AI 设计

### 4.1 模型与参数

| 角色 | 默认模型 | effort | 说明 |
|------|----------|--------|------|
| 实时翻译 | `claude-opus-5-5` | `low` | 每句一次调用，附前 4 句作语境；并发上限 3，保证顺序和延迟 |
| 实时建议 | `claude-opus-5-5` | `low` | 同一时间只跑一个；新的自动触发替换排队中的旧触发；手动提问可打断自动建议 |
| 会议纪要 | `claude-opus-5-5` | `medium` | 全文输入，流式输出 |

- 三个角色的模型都可通过环境变量单独替换（`COPILOT_MODEL` / `TRANSLATE_MODEL` / `SUMMARY_MODEL`）。建议先用同一个最强模型 + 低 effort 跑真实会议，**用数据**决定是否把翻译换成更快的小模型。
- 所有请求都开启了服务端拒答回退（`fallbacks: "default"`，beta `server-side-fallback-2026-07-01`），避免安全分类器误判时实时建议直接空白。
- **提示缓存**：会前简报（角色、目标、报价、术语）作为稳定前缀并打上缓存断点，同一场会议内的上百次调用都复用缓存。
- 系统提示中加入"延迟敏感，立即开始输出"的指示，降低首 token 延迟。

### 4.2 实时建议的输出格式

```
**建议回应**：1–3 句可以直接念出来的话（用对方正在说的语言）
↳ 同一句话的中文翻译（仅当对方语言 ≠ 你的语言时出现，让你确认自己要说的内容）
**要点**
- 2–3 条依据 / 数字 / 下一步该问什么（用用户的语言）
**注意**：仅在存在真实风险时出现（法律/商业承诺、无法核实的说法、问题里的陷阱）
```

回复语言由服务端显式判断（优先使用 STT 返回的语种标签，其次按文字脚本判断），作为 `<reply_language>` 传给模型，卡片上显示「用 English 回复」徽标。

硬性规则：事实只能来自简报、参考文件和逐字稿，**不编造价格、日期、客户和承诺**；缺信息时建议"争取时间/反问澄清"并说明需要核实什么。

### 4.3 触发策略

1. 只看**对方**的**最终句**。
2. 规则分类：问句（`？`、`吗/呢`、`什么/怎么/能不能…`、英文疑问句开头和 `can you / could you…`）→ `question`；异议（`太贵/预算/担心/竞争对手…`、`too expensive / concern / competitor…`）→ `objection`。
3. 问题有 6 秒冷却；异议不受冷却限制（更少见也更有价值）。
4. 模型判断不值得时输出 `SKIP`，前端在收到前几个字符前不会创建卡片，所以不会闪烁。
5. 用户随时可以手动提问（"怎么回应这个价格异议？"），手动请求优先。

## 5. 延迟预算（目标：对方说完 → 看到第一行建议 ≤ 2 秒）

| 环节 | 目标 | 手段 |
|------|------|------|
| 采集 + 分帧 + 上行 | ~150 ms | 100 ms 帧、AudioWorklet、WebSocket 二进制 |
| STT 端点检测（说完到最终句） | 300–700 ms | 供应商端点检测；可调灵敏度 |
| 规则触发 | < 1 ms | 正则 + 冷却 |
| 大模型首 token | 0.5–1.2 s | 低 effort、缓存简报、短上下文（最近 4 分钟）、"立即输出"提示 |
| 下行 + 渲染 | < 50 ms | 流式 delta |

后续优化：在**部分结果**阶段就做投机触发（检测到问句即预热请求，最终句确认后再展示）；对超长会议改为"滚动摘要 + 最近窗口"作为上下文。

## 6. 成本模型（按会议小时估算）

- **STT**：按音频分钟计费，两路音频 ≈ 2 × 会议分钟数（用户静音时麦克风路仍在发送；Phase 1 加客户端 VAD 只发有声片段，可明显降低成本）。单价以供应商官网为准。
- **Claude**（Opus 5.5 价格：输入 $4 / 百万 token，输出 $20 / 百万 token，缓存读取 $0.20 / 百万 token）：
  - 翻译：每句 ≈ 几百个未缓存输入 token + 几十个输出 token；一小时数百句。
  - 建议：每次 ≈ 1–3 千输入 token（最近 4 分钟逐字稿）+ 1–3 百输出 token；一小时数十次。
  - 纪要：一次，输入约等于全文逐字稿。
  - 启用低 effort 后思考 token 也会计入输出，**请以 API 返回的 `usage` 实测为准**，并在 Phase 1 接入按会议的用量统计。

## 7. 隐私、合规与信任（产品的护城河，不是负担）

- **知情同意**：开始前必须勾选"已告知所有与会者并取得同意"。新加坡 PDPA、中国《个人信息保护法》（含数据出境要求）、欧盟 GDPR，以及美国部分州的"双方同意"录音法律都对此有要求。机器人入会方案中，机器人的名字本身就会显示"会议助手"。*本节不构成法律意见，正式商用前请由法律顾问审核。*
- **数据最小化**：录音只在用户浏览器里生成和下载；服务器只在内存中转发音频给 STT，不落盘；逐字稿在会议结束后由用户导出。
- **密钥安全**：所有第三方密钥只在服务端；可选 `ACCESS_TOKEN` 和来源白名单（`ALLOWED_ORIGINS`）保护 WebSocket。
- **数据驻留**：面向中国大陆客户（腾讯会议场景）时，规划国内部署方案：自建 STT（如 FunASR / SenseVoice）+ 合规的模型接入方式。
- **企业版**：SSO、审计日志、保留期策略、与供应商签署零数据保留（ZDR）等协议。

## 8. 路线图

### Phase 0 — MVP（本次已交付）
- [x] 四平台链接识别（含整段邀请文字、Zoom 网页入会改写）
- [x] 标签页音频 + 麦克风双路采集、16 kHz 重采样、本地录音下载
- [x] Soniox / Deepgram 实时 STT 适配 + 无密钥时的能量 VAD 模拟器
- [x] Claude 实时翻译、实时建议（自动 + 手动）、会议纪要（流式）
- [x] 演示会议（无需任何密钥即可跑通完整链路）
- [x] 单元测试 + 会话集成测试 + 浏览器端到端验证；CI

**验收标准**：配置密钥后，在一场真实的中英混合 Zoom/Meet 会议中，字幕延迟 < 1 秒、翻译延迟 < 2 秒、对方提问后 2 秒内出现建议。

### Phase 1 — 质量与留存（已交付主体）
- [x] **双语回复**：建议回应用对方的语言 + `↳` 你的语言翻译；服务端显式判断回复语言
- [x] **参考文件**：PDF / TXT / Markdown / CSV 上传到 Claude Files API，按 `file_id` 以文档块附在请求中并打缓存断点；建议注明出处（来源：文件名 p.X）。
  - 设计取舍：单场会议的资料通常只有几份文件，**长上下文 + 提示缓存**比自建 RAG 更准、更省事（缓存读取 $0.20/百万 token）。翻译不附带文件（每句都调用，没必要付这部分 token）。当资料库扩大到团队级（Phase 4）时再引入检索。
  - Word/PPT 先导出为 PDF；文件保存在 Files API 中直到用户在界面上移除。
- [x] **可观测性**：每场会议的建议延迟（对方说完 → 第一个字）、翻译延迟、各角色首 token 延迟 P50/P95、token 与缓存命中、预估费用、STT 实际发送的音频时长、错误数；界面实时显示，服务端每场会议结束时输出一行结构化 JSON 日志（不含会议内容）。
- [x] **👍/👎 反馈**：计入指标（建议好评率），并随会议记录保存，作为后续评测集的来源。
- [x] **客户端 VAD**：只发送有声片段（含 300 ms 预留和 1.5 s 拖尾，保证 STT 能断句），噪声底自适应；服务端用 `AudioClock` 把 STT 时间戳映射回会议真实时间。STT keepalive 缩短到 3 秒，长时间静音也不会断流。
- [x] **说话人命名**：点击 S1/S2 改名，名字同步到服务端，用于建议、翻译上下文和纪要。
- [x] **会议历史**：会后自动保存到**本机浏览器 IndexedDB**（不上传服务器），可全文搜索标题、逐字稿、翻译和纪要，可查看、导出、删除。这样在没有账号体系前就满足"历史可查"，同时坚持隐私优先；账号 + 云端同步留到 Phase 3/4 多人协作时。
- [x] **评测工具**：
  - `npm run eval:stt`：真实 STT 按实时速度跑 `evals/stt/*.wav`，输出中英混合错误率（中日韩按字、其他按词）和断句延迟。
  - `npm run eval:copilot`：用与线上完全相同的提示词和模型跑 `evals/copilot-cases.json`（种子用例覆盖：报价引用、中文问答、价格异议不许编折扣、闲聊应跳过、未知资质不许乱承诺、日语、手动提问拒绝排他），先做确定性检查（必须/禁止提及、回复语言、是否有翻译行、是否 SKIP），再由 Claude 评审打分（有据可依 / 有帮助 / 简洁），输出报告到 `evals/reports/`。
- [ ] 部分结果投机触发（对方句子未结束时预热请求）——等真实会议的延迟数据出来再决定是否值得做
- [ ] 用真实会议（脱敏）扩充评测集，跑第一轮基线（需要 API 密钥，会产生费用）

### Phase 2 — 桌面端与稳定性（已交付主体）
- [x] **桌面应用（Electron）**：主进程内置 copilot 服务（只监听 127.0.0.1，每次启动随机访问令牌），加载同一套 Web 界面；外部链接（会议邀请）交给系统默认浏览器或会议客户端打开。
- [x] **系统声音采集**：桌面版新增「系统声音」模式，主进程用 `setDisplayMediaRequestHandler` 返回屏幕源 + `audio: 'loopback'`，可配合 Zoom / Teams / 腾讯会议**桌面客户端**使用，麦克风仍单独一路（"我/对方"分离不变）。
  - 平台说明：Electron 官方文档标注系统声音回环在 **Windows** 上支持；macOS 取决于系统和 Electron 版本（已在 Info.plist 声明 `NSAudioCaptureUsageDescription`），拿不到声音时界面会给出明确的替代方案（共享浏览器标签页，或 BlackHole 等虚拟声卡）。Linux 请使用标签页模式。
- [x] **置顶提词器**：无边框、始终置顶（可浮在全屏会议窗口之上、跨桌面空间）的小窗口，显示对方最新一句话 + 翻译、最新建议（双语）和「立即建议」按钮；默认对屏幕共享**不可见**（`setContentProtection`），主窗口同样可选隐藏，避免字幕和建议被共享出去。
  - 浏览器版同样提供「画中画提词器」（Document Picture-in-Picture API，Chrome / Edge 116+）。
- [x] **全局快捷键**：`Ctrl/⌘ + Shift + Space` 立即建议，`Ctrl/⌘ + Shift + O` 显示/隐藏提词器；会议应用在前台时也有效。
- [x] **密钥安全**：API 密钥在桌面设置中填写，用系统钥匙串（Electron `safeStorage`）加密保存在本机；界面只能看到"是否已设置"，看不到明文；系统钥匙串不可用时拒绝保存（可改用环境变量）。
- [x] **断网续会**：
  - 服务端会话在连接断开后保留 2 分钟，客户端重连时带上 `resumeSessionId` 续上同一场会议（逐字稿、STT 流、Copilot 上下文都不丢）；断开期间产生的翻译和建议排队，重连后补发。
  - 客户端在断开期间缓存音频（约 2.5 分钟），重连后以约 8 倍速补发，实时音频排在后面，保证顺序。
  - 音频帧带**采集时间戳**，服务端按采集时间而不是到达时间排时间轴，补发的音频时间也准确。
  - 用户主动结束会议时发送 `leave`，服务端立即释放会话。
- [x] 打包：`npm run desktop:package`（macOS dmg/zip、Windows nsis、Linux AppImage，未签名的测试包）
- [ ] 代码签名与公证（macOS Developer ID、Windows 证书）、自动更新——正式分发前需要
- [ ] macOS 系统声音在真机（macOS 14/15）上的验证；如不可用，评估接入 ScreenCaptureKit 原生模块

### Phase 3 — 会前、会后与自动入会（已交付主体）

目标：把工具从"会中提词器"扩展成覆盖**会前准备 → 会中 → 会后跟进**的完整工作流，并去掉"必须在本机共享标签页"的限制。

- [x] **日历订阅（ICS / iCal）**：粘贴 Google 日历 / Outlook / iCloud / 飞书等的订阅链接即可列出未来 48 小时的会议（服务端解析，支持重复会议、例外和时区；自动识别邀请中的会议链接），会前 2 分钟弹出提醒（站内横幅 + 系统通知），一键「准备」或「加入并准备」。
  - 设计取舍：先用 ICS 订阅而不是 OAuth——零配置、所有日历都支持、不需要我们托管用户的日历令牌；双向写入（改期、回复）留到 Phase 4。
  - 订阅链接只存于本机浏览器；服务端抓取走 **SSRF 防护**（只允许 https、拒绝内网/保留地址、DNS 解析后固定连接地址防重绑定、逐跳校验重定向、限制大小和时长），桌面版可访问内网。
- [x] **AI 会前简报**：根据日历事件（标题、描述、参会人）、同一重复会议或同一批人的**历史会议纪要与未完成待办**、参考文件，生成我的角色、会议目标、议程、**预计问题与建议回答**、待跟进事项和风险；使用结构化输出（JSON Schema），缺失信息标"（待确认）"而不是编造。简报进入会中 AI 的缓存上下文。
- [x] **会议结果结构化**：纪要之后提取**决定事项、待办（负责人 + 截止日期，"下周五"按会议日期和时区换算）和跟进邮件**；与纪要共用同一段缓存的逐字稿前缀，第二次调用几乎全部命中缓存。
  - 待办可勾选完成（保存在本机历史，下次同系列会议的简报会带上未完成项）、导出 CSV、加入日历（.ics 全天日程）；跟进邮件可复制或一键用邮件客户端发给参会人。
- [x] **会后推送**：一键或自动把纪要要点、决定和待办推送到**飞书、钉钉、企业微信、Slack、Teams** 群机器人，或带 HMAC 签名的**通用 JSON Webhook**（接 Zapier / Make / n8n / CRM）。
  - 各平台的签名（飞书签名校验、钉钉加签）、消息格式与长度限制分别适配；会议内容中的 @所有人 等提及会被中和；常见错误（签名不符、关键词不匹配、Webhook 失效）给出可操作的中文提示。
  - Webhook 地址只保存在本机浏览器，经服务端转发（这些平台都不允许浏览器跨域调用），同样走 SSRF 防护。
- [x] **会议机器人（自动入会）**：通过 [Attendee](https://attendee.dev)（开源，可托管或自部署）派机器人加入 Zoom / Google Meet / Teams，会议混音以 wss 实时回传，进入同一套识别 → 翻译 → 建议流程；入会后在聊天中发送录音告知，录制 mp3 供会后下载。
  - 每个机器人有随机密钥，音频 WebSocket 只接受该密钥；服务端按采样数计时、按机器人时间戳识别断流，静音段同样被 VAD 过滤以节省识别费用。
  - 界面显示入会进度（等候室需主持人准入、Zoom 需允许录制等给出提示），机器人离会后会议自动结束；手机息屏也不中断：机器人会话断线保留 15 分钟，客户端在此期间持续重连，恢复网络/回到前台时立即重连。
  - 腾讯会议暂无机器人方案，继续使用标签页 / 系统声音采集。
- [x] **「这是我」**：机器人或线下麦克风听到的是所有人，用户在字幕中把自己的说话人标记为「我」后，自己的发言不再触发建议，在提示词和纪要中也按"我"处理。
- [x] **只读实时共享**：会议中生成一次性只读链接，同事（或不懂会议语言的人）无需登录即可实时查看字幕、翻译、纪要，可选是否共享 AI 建议；跟进邮件草稿永不共享；停止共享或会议结束后链接立即失效，观看者中途加入会先收到完整快照。
- [ ] OAuth 日历（Google / Microsoft）：自动派机器人按时入会、会后把纪要写回日历事件
- [ ] 机器人逐人音轨（per-participant audio）：用平台提供的参会人姓名替代 S1/S2，自动识别"我"
- [ ] CRM / 项目管理原生集成（Salesforce、HubSpot、Jira、飞书多维表格），目前可经通用 Webhook 接入

## 9. 主要风险与对策

| 风险 | 对策 |
|------|------|
| 平台改版导致网页入会/机器人失效 | 主路线用标签页/系统音频采集，不依赖平台内部结构；机器人作为增值能力，由 Attendee 维护各平台适配 |
| 用户提供的 URL 被用来攻击内网（SSRF） | 日历和 Webhook 统一走 `safeFetch`：只允许 https、拒绝内网和保留地址、固定解析结果、逐跳校验重定向 |
| 共享链接外泄 | 链接只读、按会议一次性生成、随时可停止、会议结束即失效；不含跟进邮件草稿；不暴露服务端访问令牌 |
| 外放导致对方声音被麦克风重复采集 | 提示佩戴耳机；麦克风开启回声消除；后续在服务端按时间对齐去重 |
| 建议"一本正经地胡说" | 只基于简报和逐字稿；缺信息时建议反问；高风险内容单独标注"注意" |
| 中英混说识别差 | 默认 Soniox 多语种混说；可配置语种提示；评测集持续监控 |
| 合规风险 | 强制知情同意、本地录音、数据驻留方案、法务审核 |
| 成本失控 | 两级触发 + `SKIP`、提示缓存、客户端 VAD、按会议用量监控 |
